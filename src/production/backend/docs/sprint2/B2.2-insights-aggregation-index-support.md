# B2.2 — Detection Insights: Aggregation Pipeline & Index Support

Task: B2.2 (Shared, under B2 - Detection Insights and Analytics Extension)
Sprint: Sprint 2 - Backend

## Objective
Implement MongoDB aggregation pipeline and index support for the /insights/* routes, building on the existing /insights/overview and /insights/species routes and their start/end/species/sensorId filters.

## Part 1 - New aggregation pipeline: /insights/trends

Added a new route, GET /insights/trends, which groups detections by day using the same filter/normalization helpers already used by /insights/overview and /insights/species, so filter behaviour stays consistent across all insights routes.

The pipeline normalizes the timestamp into a Date field (`_normalizedTs`), matches on the same filters as the other routes, groups detections by day using dateToString (format `%Y-%m-%d`, UTC), sorts by date, and returns a list of {date, count} items.

### Basic testing
- GET /insights/trends returned one item grouping the current test detection by day.
- GET /insights/trends?species=Cache Test Species correctly returned the matching detection.
- GET /insights/trends?sensorId=99 correctly returned an empty result, consistent with how existing routes handle non-matching filters.

### Timestamp format check (daily totals)
The normalization stage supports two stored timestamp types: a real Date, and a string parsed with $dateFromString. Anything else is skipped. To check the daily totals for each format, 7 test events (species "TS Format Test", sensorId "ts-1") were inserted directly into the events collection. A direct insert was needed because the API only stores real Dates, and this check is about how the pipeline reads each stored format.

| Stored as | Value | Expected day (UTC) |
|---|---|---|
| Date type | 2026-09-21T10:00:00Z | 2026-09-21 |
| ISO string | "2026-09-21T11:00:00Z" | 2026-09-21 |
| ISO string with milliseconds | "2026-09-21T12:00:00.000Z" | 2026-09-21 |
| ISO string with +10:00 offset | "2026-09-22T08:00:00+10:00" | 2026-09-21 (22:00 UTC the day before) |
| ISO string with no timezone | "2026-09-22T09:00:00" | 2026-09-22 |
| Invalid string | "not-a-date" | skipped |
| Number (epoch ms) | 1758412800000 | skipped |

Result of GET /insights/trends?species=TS%20Format%20Test:
- 2026-09-21: 4
- 2026-09-22: 1

This matches the expected totals for all seven events.
- The +10:00 offset event was counted on 2026-09-21, which confirms days are grouped in UTC.
- The string with no timezone was counted on 2026-09-22, so it is read as UTC.
- The invalid string and the numeric epoch were excluded. Only Date and string types are handled, and events whose timestamp cannot be normalized are skipped without an error.

## Part 2 - Index support for insights queries

### Before
Checked existing indexes on the events collection, which /insights/* queries against. Only index present besides _id was on (sourceType, timestamp) - no coverage for species or sensorId, which are the fields /insights/species and /insights/trends filter and group by.

Ran explain() on a species-based aggregation query to confirm the impact. Result: COLLSCAN (full collection scan) - every document in events is scanned for a species-filtered query, regardless of dataset size.

### Change made
Added a new compound index to app/database.py, following the same pattern already used elsewhere in that file: a compound index on (species, sensorId, timestamp) named idx_events_species_sensor_timestamp. This runs automatically at API startup, alongside the existing index definitions.

### After - explain on the actual endpoint pipelines
The earlier version of this document reported PROJECTION_COVERED for a species-based query. That result does not hold for the actual /insights/trends pipeline, so it was re-checked as follows. A script called the app's own insights_trends() function, captured the exact pipeline it passes to Events.aggregate, and ran explain("executionStats") on that pipeline. The events collection had 9 documents at the time.

| Query | Plan | Keys examined | Docs examined | Returned |
|---|---|---|---|---|
| species + sensorId filter | IXSCAN (idx_events_species_sensor_timestamp) -> FETCH | 7 | 7 | 7 |
| start/end date range only | COLLSCAN | 0 | 9 | 9 |
| no filters | COLLSCAN | 0 | 9 | 9 |

Execution time was 0ms for all three. The dataset is too small for timings to be meaningful, so the evidence here is the plan shape and the examined counts.

- Species/sensorId filtered queries now use the new index instead of a full collection scan. The plan still includes a FETCH, so documents are read. The index narrows which documents are read, but it does not make the query index-only for this pipeline.
- The 7 events returned by the index scan include the two with unsupported timestamps. They are dropped later by the _normalizedTs match, which is why the final total is 5.
- Date-range-only queries still do a COLLSCAN. The date filter is applied to the computed _normalizedTs field, not the stored timestamp field, so it cannot use an index on timestamp. The new index also leads with species, so it does not serve date-only queries.
- Unfiltered queries do a COLLSCAN, as expected, since every document is needed.

Verified the index persists correctly by restarting the API container and re-checking db.events.getIndexes() - the new index is present and was created automatically by the application code, not just a one-off manual change.

## Findings
1. The events collection had no index support for species/sensor-based insights queries prior to this change, causing full collection scans on /insights/species and /insights/trends calls that filter by them.
2. The new compound index is used by /insights/trends when filtering by species and sensorId (IXSCAN, 7 keys and 7 documents examined on the test data), and is defined in code so it is applied consistently in every environment.
3. Not every /insights/trends query shape benefits. Date-range-only and unfiltered queries still do a COLLSCAN, because the date filter runs on the computed _normalizedTs field. Improving that would need a change to how the date filter is applied (for example also matching on the stored timestamp), and was not part of this change.
4. Daily totals are correct for the supported timestamp formats (Date, and ISO strings with Z, milliseconds, an offset, or no timezone), grouped by UTC day. Unsupported timestamp types are skipped.
5. The new /insights/trends route reuses the existing filter/normalization helpers, so it inherits the same start/end/species/sensorId filter behaviour as /insights/overview and /insights/species without duplicating logic.

## Status
Both parts of B2.2 completed: a new aggregation pipeline (/insights/trends) and index support for species/sensor-based insights queries, with timestamp-format verification and explain() evidence taken from the actual endpoint pipelines.
