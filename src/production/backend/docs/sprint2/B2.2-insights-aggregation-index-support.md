# B2.2 — Detection Insights: Aggregation Pipeline & Index Support

Task: B2.2 (Shared, under B2 - Detection Insights and Analytics Extension)
Sprint: Sprint 2 - Backend

## Objective
Implement MongoDB aggregation pipeline and index support for the /insights/* routes, building on the existing /insights/overview and /insights/species routes and their start/end/species/sensorId filters.

## Part 1 - New aggregation pipeline: /insights/trends

Added a new route, GET /insights/trends, which groups detections by day using the same filter/normalization helpers already used by /insights/overview and /insights/species, so filter behaviour stays consistent across all insights routes.

The pipeline normalizes the timestamp, matches on the same filters as the other routes, groups detections by day using dateToString, sorts by date, and returns a list of {date, count} items.

### Testing
- GET /insights/trends returned one item grouping the current test detection by day.
- GET /insights/trends?species=Cache Test Species correctly returned the matching detection.
- GET /insights/trends?sensorId=99 correctly returned an empty result, consistent with how existing routes handle non-matching filters.

## Part 2 - Index support for insights queries

### Before
Checked existing indexes on the events collection, which /insights/* queries against. Only index present besides _id was on (sourceType, timestamp) - no coverage for species or sensorId, which are the fields /insights/species and /insights/trends filter and group by.

Ran explain() on a species-based aggregation query to confirm the impact. Result: COLLSCAN (full collection scan) - every document in events is scanned for a species-filtered query, regardless of dataset size.

### Change made
Added a new compound index to app/database.py, following the same pattern already used elsewhere in that file: a compound index on (species, sensorId, timestamp) named idx_events_species_sensor_timestamp. This runs automatically at API startup, alongside the existing index definitions.

### After
Re-ran the same explain() query with the new index in place. Result: IXSCAN using idx_events_species_sensor_timestamp, and the plan is PROJECTION_COVERED - meaning the query can be answered directly from the index without reading the underlying documents at all. This is the best-case outcome for this type of query.

Verified the index persists correctly by restarting the API container and re-checking db.events.getIndexes() - the new index is present and was created automatically by the application code, not just a one-off manual change.

## Findings
1. The events collection had no index support for species/sensor-based insights queries prior to this change, causing full collection scans on every /insights/species and /insights/trends call.
2. The new compound index eliminates the collection scan entirely for these query patterns and is defined in code so it is applied consistently in every environment.
3. The new /insights/trends route reuses the existing filter/normalization helpers, so it inherits the same start/end/species/sensorId filter behaviour as /insights/overview and /insights/species without duplicating logic.

## Status
Both parts of B2.2 completed: a new aggregation pipeline (/insights/trends) and index support for species/sensor-based insights queries, with before/after explain() evidence.
