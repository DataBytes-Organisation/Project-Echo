# C14.1 - Database Consistency Checker (Report-Only + Safe-Fix)

Task: C14.1 (Owner, under C14 - Database Consistency Checker)
Sprint: Sprint 2 - Backend

## Objective
Implement a report-only consistency checker that detects orphaned/inconsistent detection-to-audio references, with an optional conservative fix mode that requires explicit confirmation.

## What was built
A standalone CLI script, tools/db_consistency_check.py, with four parts:
- find_broken_audio_links(): calls the shared scan run_consistency_checks() in app/services/consistency_checker.py (introduced in PR #1033) and keeps only the missing_audio_upload issues, meaning a detection or event whose audioClip looks like an upload reference but matches no AudioUploads record. This tool no longer has its own copy of the scan logic.
- print_report(): prints each inconsistent record's collection, record ID, sensorId, the broken audioClip value, and the reason, without dumping any audio content or other sensitive data.
- apply_conservative_fix(): only runs when explicitly requested. It replaces the broken audioClip with an empty string on the records flagged in this run. It does not delete the detection/event itself.
- verify_repairs(): after a repair, reads each repaired record back and re-runs the shared scan to confirm nothing is flagged again.

## Changes made after review
1. Repair value. The earlier version set audioClip to None. The app's models declare audioClip as a required string (schemas.py), so a detection that was valid before the repair failed validation after it. The repair now writes an empty string, which is the value the app already uses to mean "no audio clip" (serializers.py).
2. Guarded update. The update filter now matches the record's _id and the original broken audioClip value seen at scan time. If the link changed after the scan (for example someone fixed it), the record is skipped and reported, and is not overwritten.
3. Retrieval verified after repair. A repaired detection was fetched through GET /detections/{id} and returned normally (see Testing).
4. Reconciled with the checker from PR #1033. See the next section.

## Relationship to the checker from PR #1033
- Scanning is shared: this tool calls run_consistency_checks() from #1033, so there is one definition of what counts as a broken detection-to-audio link.
- The repair paths are different and are kept separate. The repair in #1033 (apply_safe_fixes, run through tools/check_consistency.py) only touches seeded fixture records (sensorId starting with C14.2-SEED-) and deletes orphaned seeded uploads. It is a fixture cleanup, not a general fix. The safe-fix in this tool works on any record flagged in the run, and only with --confirm.
- The orphan_audio_upload check from #1033 is limited to seeded uploads, so it is not used by this tool.

## CLI behaviour
- Default / --report-only: lists inconsistencies, changes nothing.
- --safe-fix without --confirm: still only reports, prints a message that no changes were made, and exits without touching the database. This logic is unchanged from the earlier version and was not re-run for this update.
- --safe-fix --confirm: applies the conservative fix, then prints the verification result.

## Testing performed
1. Ran the checker in report-only mode against the database with no broken records: correctly reported "No inconsistencies found."
2. Inserted two otherwise valid detections (species "C14 Test Species") whose audioClip pointed to upload IDs that do not exist (...00f1 and ...00f2). Report-only mode listed both records with their collection, record ID, sensorId and broken value.
3. Repair and guard test. Scanned (2 issues found), then changed the second record's audioClip to "changed-after-scan" to simulate a link changed after the scan, then ran the repair function:
   - The first record was fixed and its audioClip is now an empty string.
   - The second record was skipped and still holds "changed-after-scan", so it was not overwritten.
   - Verification returned (0, 0): no repaired record has an unexpected value, and none is flagged again by the shared scan.
4. Retrieval after repair: GET /detections/{id} for the repaired record returned HTTP 200 with the full detection and "audioClip": "".
Note: step 3 called the tool's functions directly from Python and did not go through the --safe-fix --confirm command-line flags.

## Findings
- The checker distinguishes values that are not reference-shaped at all (skipped, since they are not meant to be upload IDs) from values that are reference-shaped but match no upload (flagged).
- Report-only is the safe default. No data changes unless --safe-fix and --confirm are both passed.
- The repaired record keeps passing the app's string-field model, and it stays retrievable through the API.
- The original broken reference value is not kept after a repair, and it only appears in the report output printed before the fix. Save the report first if the old values may be needed.
- A broken reference that is not ObjectId-shaped is not detected, because the shared scan only treats 24-character ObjectId strings as upload references.

## Status
Report-only detection and the conservative fix are implemented and verified with real inconsistent records, including the schema-safe repair value, the guarded update, retrieval after repair, and reuse of the shared checker from PR #1033.
