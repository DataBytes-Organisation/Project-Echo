# C14.1 - Database Consistency Checker (Report-Only + Safe-Fix)

Task: C14.1 (Owner, under C14 - Database Consistency Checker)
Sprint: Sprint 2 - Backend

## Objective
Implement a report-only consistency checker that detects orphaned/inconsistent detection-to-audio references, with an optional conservative fix mode that requires explicit confirmation.

## What was built
A standalone CLI script, tools/db_consistency_check.py, with three parts:
- find_broken_audio_links(): scans the detections and events collections for any audioClip value that looks like an upload reference (a valid ObjectId-shaped string) but does not match any real record in AudioUploads.
- print_report(): prints each inconsistent record's collection, record ID, sensorId, the broken audioClip value, and the reason, without dumping any audio content or other sensitive data.
- apply_conservative_fix(): only runs when explicitly requested, and only clears the broken audioClip field (sets it to null) on records that were just flagged - it does not delete the detection/event itself and does not guess a replacement value.

## CLI behaviour
- Default / --report-only: lists inconsistencies, changes nothing.
- --safe-fix without --confirm: still only reports, prints a message that no changes were made, and exits without touching the database.
- --safe-fix --confirm: applies the conservative fix described above.

## Testing performed
1. Ran the checker against the current database with no known-broken records: correctly reported "No inconsistencies found."
2. Inserted one detection directly into MongoDB with an audioClip value that does not correspond to any real AudioUploads record (a placeholder ObjectId).
3. Re-ran the checker in report-only mode: correctly detected and reported the broken record, including its collection, record ID, sensorId, and the invalid audioClip value.
4. Ran the checker with --safe-fix (no --confirm): correctly reported the same issue again and explicitly stated that no changes were made, confirming the safe-fix default behaviour requires explicit confirmation.
5. Ran the checker with --safe-fix --confirm: the broken audioClip field was cleared on the flagged record.
6. Re-ran the checker in report-only mode again: correctly reported "No inconsistencies found," confirming the fix was applied correctly and the check is idempotent.

## Findings
- The checker correctly distinguishes between values that are not reference-shaped at all (skipped, since they are not meant to be upload IDs) and values that are reference-shaped but do not match a real upload (flagged as inconsistent).
- Report-only is the safe default; no data is changed unless both --safe-fix and --confirm are passed together.
- The conservative fix only clears the broken reference rather than deleting or guessing data, keeping the fix minimal and reversible-in-spirit (the underlying detection/event record is preserved).

## Status
Report-only detection and safe-fix behaviour both implemented and verified end-to-end with a real inconsistent record, matching the expected evidence in the Sprint 2 guide (known inconsistent records detected correctly, report-only default demonstrated, safe-fix behaviour documented).
