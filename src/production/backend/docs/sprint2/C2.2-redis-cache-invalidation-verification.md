# C2.2 — Redis Query Cache: Query Selection & Invalidation/Performance Verification

**Task:** C2.2 (Shared, under C2 – Redis Query Cache with Invalidation)
**Sprint:** Sprint 2 — Backend

## Objective
Select suitable MongoDB queries for caching and verify invalidation/performance
behaviour of the Redis query cache built for C2.1, using `/insights/species` and
`/insights/overview` as the target routes.

## Setup
- C2.1's caching implementation (`app/cache.py`) is on a separate, not-yet-merged
  branch/PR at the time of this testing. To verify it end-to-end, that branch was
  checked out locally and the API container was rebuilt to pick up its added dependency.
- The API container was recreated from `src/deployment/docker/docker-compose.yml`
  (`docker compose up -d --force-recreate echo_api`). Before that, `/insights/species`
  returned a 500 (`ServerSelectionTimeoutError`) because the running container did not
  have `MONGO_URI` set, and `insights.py` reads that variable, so it fell back to
  `localhost:27017`. The compose file on this branch sets `MONGO_URI` for `echo_api`.
- Cache: Redis DB 2, key prefix `insights:`, TTL 300s, isolated from HMI JWT/session
  Redis usage and from the separate job-queue Redis DB, matching the intended design.

## What was tested

### 1. Cache miss → cache set
- Cleared the cache first (`redis-cli -n 2 FLUSHDB`).
- `GET /insights/species` (first call): returned live data and created the Redis key
  `insights:species:10` in DB 2 (confirmed via `redis-cli -n 2 --scan`).
- Result: one species, `Cache Test Species` (count 1), left over from earlier test
  data. Response time 76ms.

### 2. Cache hit
- A second identical `GET /insights/species` returned the same response in 6ms.
- The key `insights:species:10` was present with TTL `252`, counting down, not reset.
  This confirms the second call was served from cache.

### 3. Invalidation check through the normal write path
This replaces an earlier version of this test that inserted directly into MongoDB. That
version did not test the application write path (direct database writes bypass any
application invalidation hook) and it wrote to `detections`, while the
`/insights/species` aggregation reads from `events`.

- With the cache warm (key TTL `60`), sent a real write through the API:
  `POST /engine/event` with a valid payload and a new species
  (`Invalidation Test Species`). Response: `201 Created`, and the event was stored in
  the `events` collection, which is the collection `/insights/species` reads.
- Immediately called `GET /insights/species` again:
  - Result was unchanged: only `Cache Test Species` (count 1), so the new species was
    not visible.
  - The key was still present and its TTL kept counting down (`60` → `56`), so it was
    not cleared by the write.
- Then flushed the cache manually (`redis-cli -n 2 FLUSHDB`) and called
  `GET /insights/species` again. The result now contained both `Cache Test Species`
  and `Invalidation Test Species`.

| Stage | `/insights/species` result |
|---|---|
| Uncached (empty cache) | `Cache Test Species` x1 (76ms) |
| Warmed cache | Same result (6ms) |
| After `POST /engine/event` with a new species | Same old result (stale), key not cleared |
| After manual cache flush | Both species returned |

- Conclusion: the write changed the underlying data, but the cached response kept
  serving the old result until the cache was flushed manually. With the current code,
  a normal application write to `events` does not invalidate the cached
  `/insights/species` response. It only refreshes when the TTL expires (up to 300s).
- Scope: this was tested for `/insights/species` and `POST /engine/event` only.
  `/insights/overview` and `POST /detections` were not tested here (`POST /detections`
  is currently blocked by the missing budget rule, see A2.2).

### 4. Code finding (separate from the experiment above)
- `grep -rn "invalidate_insights" src/production/backend/` shows an
  `invalidate_insights()` function defined in `app/cache.py` (line 85) that is never
  called anywhere in the codebase.
- This is a code-level finding on its own. The experiment in section 3 is what
  demonstrates the behaviour, and this finding explains the likely cause.

### 5. Latency comparison
- In the run above, uncached was 76ms and cached was 6ms.
- An earlier run on the same near-empty dataset showed almost identical times
  (roughly 118-121ms both ways), so single-request timings on such a small dataset are
  noisy and should not be over-interpreted. A repeated test on a larger dataset would
  give a more reliable comparison.

## Findings
1. **Cache miss/hit flow works correctly.** Cache creation, TTL countdown and identical
   cached responses on repeat calls were all confirmed.
2. **Invalidation after a write does not happen yet.** A real write through
   `POST /engine/event` left the cached `/insights/species` response stale and the key
   in place until the cache was flushed manually.
3. **Unused helper (code finding).** `invalidate_insights()` exists in `app/cache.py`
   but is never called.
4. **Suggested next step:** call `invalidate_insights()` (or an equivalent per-key
   invalidation) from the write path for `events` (`POST /engine/event`), then re-run
   the same uncached / warmed / after-write comparison to confirm the response updates
   immediately. Any other write path that changes what the insights queries read
   should be checked the same way.
5. **Latency benefit** is visible in one run (76ms vs 6ms) but not consistent across
   runs at this data volume. Re-test with larger fixture data (see C13 fixture
   generator) once available.

## Status
Query selection confirmed (`/insights/species`, `/insights/overview` as cached routes).
Cache hit/miss flow verified working as designed. Invalidation-after-write was tested
through the normal write path for `/insights/species` and is not working yet. This is
consistent with `invalidate_insights()` never being called. Latency comparison is
inconclusive at current data volume.
