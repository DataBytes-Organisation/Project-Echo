# C2.2 — Redis Query Cache: Query Selection & Invalidation/Performance Verification

**Task:** C2.2 (Shared, under C2 – Redis Query Cache with Invalidation)
**Sprint:** Sprint 2 — Backend

## Objective
Select suitable MongoDB queries for caching and verify invalidation/performance
behaviour of the Redis query cache built for C2.1, using `/insights/species` and
`/insights/overview` as the target routes.

## Setup
- C2.1's caching implementation (`app/cache.py`) is on a separate, not-yet-merged
  branch/PR at the time of this testing. To verify it end-to-end, that branch was
  checked out locally and the API container was rebuilt
  (`docker compose up -d --build echo_api`) to pick up its added dependency.
- Cache: Redis DB 2, key prefix `insights:`, TTL 300s, isolated from HMI JWT/session
  Redis usage and from the separate job-queue Redis DB — matching the intended design.

## What was tested

### 1. Cache miss → cache set
- `GET /insights/species` (first call): returned live data, and created a new Redis key
  `insights:species:10` in DB 2 (confirmed via
  `redis-cli -n 2 --scan --pattern "insights:*"`). This part works as designed.

### 2. Cache hit
- TTL on `insights:species:10` was `269`.
- A second `GET /insights/species` call returned the identical response, with TTL
  counted down to `268` (not reset) — confirming the second call was served from cache
  as intended.

### 3. Invalidation check
- Inserted a new detection directly into MongoDB (`db.detections.insertOne(...)`) with a
  new species value (`Invalidation Test Species`), while the `insights:species:10` cache
  entry was still active (TTL `185`).
- Immediately re-checked TTL and re-called the endpoint:
  - TTL was still counting down normally (`185`).
  - `GET /insights/species` still returned only the earlier cached result and did not
    yet include the newly inserted detection.
- This shows that, at the time of testing, a write to the `detections` collection does
  not yet trigger cache invalidation — the cached response updates only once the TTL
  naturally expires (up to 300s).

### 4. Investigation
- `grep -rn "invalidate_insights" src/production/backend/` shows an
  `invalidate_insights()` function already defined in `app/cache.py` (line 85), which
  looks intended for exactly this purpose. At the time of testing it doesn't appear to
  be called yet from a write path (e.g. `POST /engine/event`, `POST /detections`) —
  likely just not wired up yet, since C2.1 is still in progress/under review.

### 5. Latency comparison
- Cache miss (uncached) vs cache hit (cached) response times were measured with the
  current local dataset and found to be very close (roughly 118-121ms either way).
- This is expected given the small size of the local test dataset — the benefit of
  caching should be clearer once tested against a larger, more realistic dataset where
  the underlying MongoDB aggregation is more expensive.

## Findings
1. **Cache miss/hit flow works correctly** — confirmed cache creation, correct TTL
   behaviour, and identical cached responses on repeat calls.
2. **Invalidation-after-write isn't wired up yet.** The `invalidate_insights()` helper
   already exists and looks like the right mechanism — it just isn't being called from
   the detection/event write paths yet. Flagging this so it can be connected up as part
   of finishing C2.1/C2.2 together.
3. **Suggested next step:** call `invalidate_insights()` (or an equivalent per-key
   invalidation) from the write paths (`POST /engine/event`, `POST /detections`, and any
   bulk-insert path) so cached insights responses clear immediately after a relevant
   write, rather than only via TTL expiry.
4. **Latency benefit not yet clearly measurable** at current data volume — recommend
   re-testing with larger fixture data (see C13 fixture generator) once available.

## Status
Query selection confirmed (`/insights/species`, `/insights/overview` as cached routes).
Cache hit/miss flow verified working as designed. Invalidation-after-write is the one
remaining piece to connect, and a likely mechanism (`invalidate_insights()`) is already
in place. Performance comparison inconclusive at current data volume — documented as a
known testing-conditions limitation, not a code issue.

## Next steps / dependencies
- Wire `invalidate_insights()` into detection/event write paths (as part of C2.1/C2.2).
- Re-run latency comparison once realistic fixture data volume is available.
